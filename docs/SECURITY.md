# Security Model

`brand-bridge` is the integration layer between brand back-office systems and AI hosts. The security boundary lies between the AI host and the brand backend; the platform is responsible for keeping that boundary trustworthy.

## Threat model

Trusted: brand engineers, operators with audit log access, the brand backend itself.
Semi-trusted: AI hosts (Claude Desktop, ChatGPT, etc.) — bound by JWT scope.
Untrusted: end users prompting the AI, anyone holding a forged or replayed token.

The platform assumes the AI host can hallucinate, retry, or be tricked into calling unintended tools. Every defensive primitive below targets that scenario.

## Defenses by layer

| Concern | Mechanism | Where |
|---|---|---|
| Tool-scope abuse | JWT scope + `audited_tool` decorator | `core/audit.py` (M1), `auth/jwt_scope.py` (M2) |
| Burst / DoS / runaway agent loops | Sliding-window rate limit, configured per L0–L3 class | `core/audit.py::RateLimiter` |
| Duplicate writes from agent retries | Idempotency store with body-hash check | `core/audit.py::IdempotencyStore` |
| Skipping the user-confirm step | Confirmation tokens — single-use, 5-min TTL, generated by `calculate_price`, consumed by `place_order` | `core/audit.py::generate_confirmation_token` |
| PII leakage | Phone/email masking in formatters | `core/audit.py::mask_phone/mask_email` |
| ID enumeration | Random short-token IDs (`ord_xxx`, `addr_xxx`) — adapters MUST follow this | adapter convention |
| Cross-tenant access | Tenant routing at request entry; `ToolContext.tenant_id` is the only legitimate source of truth | `registry/tenant.py` |
| Untraceable changes | Every tool invocation appended to `AuditLog` (in-memory ring buffer, persistent backend in M2) | `core/audit.py::AuditLog` |

## Risk classes (L0–L3)

Tools self-declare a risk class via the `audited_tool` decorator. Class drives the default rate limit pulled from `tenant.yaml`.

| Class | Surface | Default limit | Examples |
|---|---|---|---|
| L0 | Public read | 60 / 60s | `list_stores`, `list_products`, `now_time_info` |
| L1 | User-context read | 30 / 60s | `my_account`, `my_coupons`, `my_orders` |
| L2 | Low-risk write | 5 / 3600s | `create_address`, `claim_coupon` |
| L3 | High-risk write | 10 / 86400s | `place_order`, `redeem_points`, `cancel_order` |

Brands can override these in `tenant.yaml`. Lowering an L3 class warrants a security review — your AI host is the primary mitigation against runaway loops.

## Confirmation-token flow

```
AI host                                    brand-bridge platform                 brand POS
──────                                     ─────────────────────                  ─────────
calculate_price({items})  ─────────►       generate_confirmation_token()
                                            register_confirmation_token(t, q)
                                            return PriceQuote(t, ...)
   ◄────  PriceQuote{confirmation_token=t}
   (AI shows quote to user)
   (user approves)
place_order({t, idem_key, ...})  ──────►   consume_confirmation_token(t)
                                            (raises if missing/expired/reused)
                                            DEFAULT_IDEMPOTENCY_STORE.lookup(...)
                                            (returns cached order if dup)
                                            adapter.place_order(...)        ──►   POST /orders
                                            DEFAULT_IDEMPOTENCY_STORE.store(...)
   ◄────  Order
```

The token is single-use and expires in 5 minutes. An AI host that drops the token (or gets it from a stale tool result) cannot place the order — it must call `calculate_price` again.

## Idempotency contract

L3 tool callers must supply `idempotency_key`. The platform:

1. Computes `body_hash = sha256(canonical_json(request))`.
2. Looks up `(tenant_id:tool, key)` in the store. If present and `body_hash` matches, returns the cached response without calling the adapter.
3. If present but `body_hash` differs, raises `IdempotencyError` — the AI host must use a fresh key for a different request.
4. If absent, runs the adapter and caches the response under the (key, body_hash).

Keys are caller-generated (UUIDs are typical). The store TTL is 24h.

## Audit log

Every wrapped tool call appends an `AuditEntry`:

```python
AuditEntry(
    tool="place_order", tenant_id="my_brand", user_id="USER_001",
    success=True, duration_ms=187,
    timestamp="2026-05-07T14:32:11.412Z", error="",
)
```

The default backend is an in-memory ring buffer (10k entries). M2 will add a SQLite-backed store + REST endpoint (`GET /api/audit?tenant=...`) gated behind operator scope.

## What the platform does NOT do

- **Authentication of the end user.** The brand backend's OAuth / session token is what proves identity; the platform forwards `X-User-Id` from a verified header.
- **Encryption at rest of brand secrets.** Use environment variables or your secrets manager — `brand-bridge` reads but does not store API keys.
- **Webhook signature verification for brand POS callbacks.** The brand's `IMChannelProvider.verify_webhook` is responsible for this; the platform calls it but does not implement HMAC for vendors.

## Reporting vulnerabilities

Email security@lumitive.example with a description and proof of concept. We aim to acknowledge within 48 hours and ship a patch within 7 days for high-severity issues. Do not open a public GitHub issue for security reports.
